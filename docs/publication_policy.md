# GRADE Publication Policy

**Package:** `grade 0.1.0.dev0` · Related: [`docs/methodology.md`](methodology.md)

This document defines the public/private boundary for the GRADE benchmark package and
the four-part litmus test applied before any artifact is published. It is the reference
document for publication review (G-QA).

---

## Purpose

GRADE is designed to be fully open: the task definitions, fixture data, scoring rubrics,
schemas, runner code, methodology, and dataset cards are all intended for public
distribution. Publication review exists to confirm that nothing in the published artifacts
inadvertently reveals implementation details that belong to the private systems this
benchmark was developed alongside.

The boundary is not about protecting competitive advantage — it is about ensuring that
GRADE teaches the outside world what good education-analytics behavior looks like, not
how any particular private system is built.

---

## Open Boundary (Safe to Publish)

The following artifact categories are safe to publish as part of the `grade` package
or the benchmark website:

- **Task definitions** — the benchmark questions, gold facts, gold insights, forbidden
  claims, required limitations, and rubric weights in `benchmark/tasks/` and
  `benchmark/tracks/`.
- **Fixture schemas and data** — the column contracts in `benchmark/schemas/fixture_schema.md`
  and all generated fixture files in `fixtures/`. All fixture data is fully synthetic;
  no real student, tutor, school, or program records are included.
- **Scoring rubrics and scorers** — the C1–C4 scoring modules in `benchmark/rubrics/`
  and the C9 scorecard generator in `benchmark/reports/`.
- **Output and result schemas** — `output_schema.json`, `result_schema.json`,
  `task_schema.json` in `benchmark/schemas/`.
- **Runner code and adapters** — the generic CLI runner in `runner/` and the model
  adapter examples in `examples/`.
- **Methodology and dataset cards** — all files in `docs/`.
- **Benchmark reports** — scorecard reports rendered by C9, including leaderboard
  scores and per-task results.
- **Example model outputs** — normalized response objects conforming to
  `output_schema.json` and used for scorer testing.

---

## Private Boundary (Keep Internal)

The following artifact categories must not appear in the `grade` package or any public
documentation:

- **System prompts used in private production deployments** — even if they describe
  education-analytics behavior, they reveal how a specific product is configured.
- **Internal tool names, routing logic, or orchestration architecture** — how a private
  system dispatches requests, selects tools, or structures multi-step reasoning.
- **Internal response schemas or log formats** — raw response objects, internal
  tracing fields, internal tool-call records, or any schema fields that are not part of
  the published `output_schema.json`.
- **Private evaluation harnesses** — if an organization runs GRADE internally against
  its own system, the adapter code, system-prompt wiring, and internal comparison results
  stay private. Only the normalized benchmark scores may be published.
- **Anything production-shaped** — any artifact that, if read by a technically
  sophisticated outside party, would reveal how a private deployed system works rather
  than what good education-analytics analysis looks like.

## Four-Part Litmus Test

Before any artifact is added to the `grade` repository or published on the benchmark
website, it must pass all four of the following checks. G-QA executes this checklist
as a hard gate before launch.

### 1. Data Review

> Does this artifact contain or reference real student, educator, program, or
> institutional data?

**Pass criteria:** The artifact contains only:

- Fully synthetic data generated by `benchmark/datagen/generator.py` with a documented
  integer seed.
- Published research citations (properly attributed).
- Fictional program names, school names, and entity identifiers created for benchmark
  purposes.

**Fail criteria:** Any row, record, name, identifier, or statistic traceable to a real
person, school, district, or program — even if anonymized or aggregated.

### 2. Contract Review

> Does publishing this artifact create legal, regulatory, or contractual exposure?

**Pass criteria:** The artifact:

- Contains no data subject to FERPA, COPPA, HIPAA, or state student-privacy laws.
- Does not reproduce copyrighted material beyond fair-use excerpts (research citations
  must be limited to title, author, year, and a brief key-finding summary).
- Does not violate any data-sharing agreement, memorandum of understanding, or
  contractual data use restriction.

**Fail criteria:** Any artifact that would trigger a data-privacy regulation or
breach a data use agreement, regardless of intent.

### 3. Implementation Review

> Does this artifact reveal how a private deployed system is built, rather than
> how a good analyzer should behave?

**Pass criteria:** A technically sophisticated reader could use the artifact to
understand what a high-quality education-analytics response looks like, and could
evaluate any AI system's responses against it — but could not infer the internal
architecture, prompt design, or tool structure of any specific private deployment.

**Fail criteria:** Any of the following appear:

- A system prompt, partial system prompt, or prompt template from a private production
  system.
- Internal tool names (function names, API endpoint names, plugin identifiers).
- Internal routing logic, orchestration patterns, or multi-step planning templates.
- Log-format fields, internal schema keys, or response-wrapper structures unique to a
  private deployment.
- Benchmark rubric guidance that encodes private-system behavior as a gold standard
  (e.g., "the model should respond in the format used by [private product]").

### 4. Positioning Review

> Does this artifact accurately represent GRADE as an independent benchmark, or does
> it position it as an evaluation of a specific private product?

**Pass criteria:** The artifact:

- Describes GRADE as a general-purpose benchmark for AI systems analyzing education
  program data — evaluable by any model.
- Uses vocabulary appropriate for educator and analyst audiences, not internal product
  terminology.
- Makes no comparative claims about specific private products without independently
  verified benchmark results.

**Fail criteria:** Any artifact that:

- Names a private product as the primary intended subject of evaluation.
- Uses internal product vocabulary (codenames, feature names, team names) in
  task descriptions, rubric guidance, or methodology text.
- Claims benchmark results for a private product without a corresponding published
  `results.json` artefact.

## Vocabulary Check

The following terms are internal and must not appear in any published GRADE artifact.
If a reviewer encounters them, the artifact fails the Implementation Review check.

If you are authoring a task, rubric, or documentation file, use the right-column
substitution instead.

| Internal term (not for publication) | Acceptable substitution |
|---|---|
| Internal product / tool codenames | "the AI system under evaluation" or the model ID |
| Internal API endpoint names | describe the capability generically (e.g., "the model's response") |
| Internal response schema field names not in `output_schema.json` | use only published schema fields |
| Internal team or project names | omit; use "the benchmark authors" if attribution is needed |

---

## Applying This Policy

**Before opening a PR to `grade`:** Run through the four-part litmus test mentally.
If any check is uncertain, flag for G-QA review before merging.

**G-QA gate:** G-QA (#612) executes the checklist programmatically and via human review
before the launch runbook (G4) can be executed. A G-QA failure blocks launch.

**After launch:** The policy applies to all future additions. PRs that add new tasks,
fixtures, rubrics, or documentation are subject to the same four-part review. The
`CODEOWNERS` file designates the maintainer responsible for publication review sign-off.
